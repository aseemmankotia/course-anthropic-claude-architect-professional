## Chapter 10: Developer Productivity and Operational Enablement — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Precedence order of Claude Code settings sources, highest to lowest? | Enterprise managed policy > command line arguments > local project settings (.claude/settings.local.json) > shared project settings (.claude/settings.json) > user settings (~/.claude/settings.json). Exam tip: enterprise policy always wins — this is how platform teams enforce guardrails. |
| 2 | Three places a CLAUDE.md file can live, in order of scope (broadest to narrowest)? | Enterprise-level managed memory (IT-deployed) → project-level ./CLAUDE.md (shared via git) → user-level ~/.claude/CLAUDE.md (personal, all projects). Exam tip: project CLAUDE.md should extend, not duplicate, enterprise conventions. |
| 3 | Where do project-level subagents live, and why does scope matter? | .claude/agents/*.md committed to the repo. Project-level agents are shared with every contributor and take precedence over same-named user-level agents in ~/.claude/agents/. Exam tip: commit subagents to share them across a team. |
| 4 | What's the key difference between an Agent Skill and instructions in CLAUDE.md? | A Skill packages instructions plus supporting files as a discrete, versionable, shareable unit reusable across projects. CLAUDE.md content is project/user-scoped context, not a portable package. Exam tip: use Skills for reusable workflows, CLAUDE.md for persistent project context. |
| 5 | What does an internal MCP server catalog provide that ad-hoc configuration doesn't? | Centralized discovery, documented capabilities/scopes, and standardized onboarding so teams self-serve instead of duplicating MCP server setup. Exam tip: catalogs reduce duplicated effort across teams — a core platform-enablement artifact. |
| 6 | What four things must an operational runbook for agent incidents define? | Detection, containment (e.g., revoke credentials/branch protection), rollback steps, and escalation path. Exam tip: runbooks are reactive/incident artifacts, distinct from preventive conventions like CLAUDE.md rules. |
| 7 | Platform team responsibility vs individual developer responsibility — give one example of each. | Platform team: enterprise settings, shared skill/subagent libraries, MCP catalog. Individual developer: project-specific business logic in local CLAUDE.md, personal CLI preferences. Exam tip: exam distinguishes org-wide infra ownership from per-developer customization. |
| 8 | Which metrics best measure developer productivity impact of a Claude Code rollout? | Lead time for changes, PR cycle time, and self-reported time saved on repetitive tasks — measured against a pre-rollout baseline. Exam tip: avoid vanity metrics like token usage or number of CLAUDE.md files; tie measurement to delivery outcomes. |
| 9 | Why layer CLAUDE.md conventions (enterprise → project → user) instead of letting every team freewheel? | Layering gives consistent baseline behavior org-wide while still allowing project-specific context, preventing the unpredictable agent behavior caused by 40 teams writing inconsistent conventions independently. Exam tip: this is the standard scaled-rollout pattern. |
| 10 | How is an MCP server typically added at project scope so the whole team shares it? | Via a .mcp.json file committed to the repository (project scope), as opposed to local/user scope which is personal to one developer's machine. Exam tip: project scope = shared via version control; user/local scope = not shared. |
| 11 | Common exam trap: team disables CLAUDE.md entirely after inconsistent conventions caused problems. Why is this wrong? | It removes valuable persistent project context and hurts productivity instead of fixing the root cause. Correct fix: standardize via a shared template/enterprise base file, not removal. Exam tip: the fix is governance, not elimination. |
| 12 | Common exam trap: using CLAUDE.md to enforce which MCP servers are trusted org-wide. Why is this wrong? | CLAUDE.md is a memory/context file, not an enforcement mechanism — it's a comment/suggestion a developer could ignore or edit. Enterprise managed settings (top of precedence hierarchy) are required for actual enforcement. Exam tip: memory ≠ policy. |
